# 代码评审

先冻结比较点，再沿仓库规范和预期行为两个独立轴进行评审。

## 操作流程

1. 确认 base、head、diff 范围、需求说明、测试证据和用户给出的证据预算；查询数、文件数和只读限制必须原样执行。
2. 使用一次最聚焦的索引或 diff 查询定位风险面，再检查规范和确定性工具失败；不要用全仓库扫描重复同一发现，也不要重复抄写工具输出。
3. 根据需求说明检查行为、边界情况、数据和失败路径。
4. 对正确性、复杂度、冗余、性能、架构和测试质量逐项形成证据判断，特别检查无调用方层级、复制逻辑、过度读取和重复计算。
5. 只报告可执行的问题，并包含证据、影响、级别和位置。
6. 把两个评审轴合并为 `QualitySnapshot` 门禁；告警、失败、未评估或未关闭修复项不得通过。

默认只打开能支持或推翻一个具体结论的最小证据集。索引已经返回的源码不得重复读取；除非被评审对象就是插件，否则不得扫描插件实现、validator、memory 或历史 rollout。达到用户预算后，未覆盖维度应标为未评估，不得继续扩张上下文。

当前源码、配置和运行结果与历史报告冲突时，以当前事实为准并把报告标为陈旧。安全评审必须追踪秘密或授权数据的全部扇出路径，包括主表、outbox、通知 payload、URL、日志、审计和错误信息；“主表只存摘要”不能证明其他旁路没有持久化原文。最终答复只能声明实际执行过的文件数、工具和验证，不得把计划或预算写成已完成事实。

安全评审的证据预算先用于闭合 `产生 -> URL/消息 -> payload -> outbox/持久化 -> dispatcher/provider/log` 链路，再检查 UI 或一般配置。索引只返回符号但未返回关键持久化、dispatcher 或测试源码时，必须用剩余预算按精确符号或路径读取该文件；不得把可由当前源码确认的事实降级成“可能”，也不得在秘密链尚未闭合时把预算花在非关键界面证据上。

需要校验 Runtime 结构化产物时，只使用已公开的 `<plugin-root>/engineering-assistant/bin/ea artifact-validate --kind <kind> --input <path>`；`plugin-root` 是当前 `SKILL.md` 所在 `skills/<id>/` 的上两级目录。若历史 StageRunResult 不属于当前支持的 `step-result` 等 kind，记录命令的非零结果、明确标记版本不兼容并停止，不得扫描插件目录寻找已删除的 validator。

阶段审计未给出预算时，继承工程助手的默认上限：一次索引查询、八个证据文件和六个 shell 命令。先读取用户明确点名的阶段结果、自测、代码评审和运行证据，再用剩余名额核对当前源码；用户要求“综合”多个点名证据时，每一类都必须独立读取，不能只读取 StageRunResult 后转述其中的摘要或链接。索引查询必须包含 diff 中的秘密、鉴权、持久化和外部动作高风险符号。一个命令批量输出多个文件仍按实际文件数计数；`find`、`rg --files`、catalog 或历史清单只能用于定位，不能成为绕过证据预算的旁路。

只有仓库规范缺失或不完整时才读取 [references/smell-baseline.md](references/smell-baseline.md)。

未检查固定 diff 前，不得仅凭摘要批准。
