# 测试驱动开发（TDD）

先明确预期行为、公共测试边界和最小验证命令，再判断本次是否适合由失败测试驱动。新增业务规则、状态转换和可复现的逻辑缺陷通常适合；用户或适用项目规范明确要求 TDD 时遵守。

文案、格式、无行为变化的元数据和已有有效覆盖的行为保持重构，不默认进入红绿循环。误选本 skill 时直接采用适用的静态检查或定向回归并说明结果，不重新调用路由器来确认同一选择，也不转交另一插件的同名 skill。正式 flow 中不适用的 TDD 节点按 Runtime 合同记录跳过理由，后续质量和人工门禁仍有效。

## 红绿反馈

1. 复用能识别目标问题的已有失败测试；缺少覆盖时才补最小行为测试。先实际运行，确认失败源于目标行为，而非环境、导入或夹具错误。
2. 实现满足该行为的最小改动，再运行同一测试和相关回归。测试已有足够覆盖时不添加重复用例，不为展示红灯破坏正确实现。
3. 仅在改善本次实现确有必要时重构，并保持回归通过。发现范围外死代码只提示，不附带删除或清理。

测试应观察业务结果或公共契约，避免复刻实现。只有必须控制真实依赖边界时才读取 [references/mocking.md](references/mocking.md)。行为触及身份或授权状态、认证或秘密解析、编码归一化、审计或持久化 adapter 合同时才读取 [references/security-seams.md](references/security-seams.md)。

报告实际执行的检查、结果和剩余缺口；不固定输出六维报告，也不在此重复提交正式质量节点的产物。相关检查通过后，仅因新改动、失败或未解决风险追加验证。缺少运行条件时继续独立工作，如实标记未验证；必要门禁不能据此视为通过。输入和环境未变的确定性失败不原样重试。

已在实现后补测时如实说明顺序，不补造红灯记录。完成标准是已选行为通过适用验证；不适用 TDD 的任务不声称完成过红绿循环。
