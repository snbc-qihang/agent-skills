# YQ 架构巡检治理规则

适用场景：对 `/Users/sunliming/work/project/snbc/yq` 或萤启/人人取相关多服务系统做架构巡检、领域划分、服务边界、数据边界、治理路线分析。

## 1. 阶段顺序

必须先完成第一阶段架构规划，不能直接进入具体问题治理。

第一阶段必须先定：
- 萤启和人人取的总体架构关系
- 领域划分
- 业务能力划分
- 数据边界划分
- 萤启-人人取架构图
- 萤启领域架构图

在这些内容未确认前，不要输出：
- MQ listener 改造方案
- Feign fallback 治理方案
- 表级迁移计划
- 服务拆分方案
- 具体代码重构清单

## 2. 已确认的一阶段架构基线

- D1：萤启业务系统 + 人人取基础能力平台。
- D2：会员数据和会员业务属于萤启。
- D3：人人取平台维护标准订单；萤启在标准订单之上完成 SVIP 订单、随单购卡等定制化功能。
- D4：平台防腐层；承接 API/MQ/DTO 转换/状态映射/副本同步。
- D5：标准商品、价格策略计算与下发属于人人取；萤启扩展定制化商品、价格策略、场景价维护。
- D6：设备/开门基础能力偏人人取平台；经营关系和履约扩展属于/偏萤启。
- D7：优惠券完全属于萤启业务。

## 3. 领域基线

萤启核心域：
- 交易履约域
- 会员权益域
- 营销活动与券域

萤启支撑域：
- 加盟商/服务商经营域
- 商品与售卖策略域
- 设备售卖与开门协作域

萤启通用/集成域：
- 平台防腐层

人人取平台能力：
- 标准订单
- 标准商品
- 价格策略计算与下发
- 支付
- 设备/开门基础能力
- 组织权限等基础能力

## 4. 数据边界口径

先判断数据类型，再讨论表级切割：

| 数据类型 | 归属口径 |
| --- | --- |
| 平台基础事实 | 人人取拥有真实修改权，萤启通过 MQ/API 保留副本或引用 |
| 萤启业务事实 | 萤启拥有真实业务含义和修改权 |
| 平台数据副本 | 萤启保存、转换、查询，但不拥有平台真实修改权 |
| 集成治理数据 | 萤启拥有，例如消息原文、幂等、同步水位、补偿记录 |
| 会员数据 | 萤启 |
| 优惠券数据 | 萤启 |
| 商品扩展/场景价数据 | 萤启；标准商品和标准价格策略计算下发属于人人取 |
| 设备经营关系/履约扩展 | 萤启；设备/开门基础能力属于/偏人人取 |

## 5. 证据与讨论规则

任何没有实际代码支撑或已有文档支撑的内容，不得写成最终结论。

处理方式：
- 有代码证据：标注 `code_evidence`，给路径/类/方法/表。
- 有文档证据：标注 `doc_evidence`，给文档路径/章节。
- 基于证据推导：标注 `inferred`，写明推导链和不确定性。
- 无证据但需要推进：标注 `assumption`，进入讨论项，不进最终结论。
- 用户/评审确认：标注 `decision`，记录决策、影响范围和后续动作。

## 6. 人机分层输出

人工只看结果，不看分析过程。

人工产物：
- 结论
- 影响
- 风险
- 待决策项
- 架构图
- 下一步动作

机器产物：
- 原始扫描数据
- 代码路径/类/方法/行号
- Feign/MQ/DB/Redis/Controller/Mapper 清单
- evidence_level
- 推导链
- 不确定性
- 产物引用关系

## 7. 常见误区

- 把 `mp-mall`、`franchisemanagement`、`coupon-activity` 当成领域边界。
- 未确认第一阶段架构基线前，就进入 MQ/Feign/事务/长类治理。
- 把 Feign 调用直接等同于目标业务边界。
- 把平台副本误当成萤启拥有的平台基础事实。
- 把候选判断写成最终结论。
