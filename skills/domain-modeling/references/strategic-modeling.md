# 战略领域建模

先确定语言和模型的适用边界，再讨论实现边界。领域是问题空间；子域是具有独立业务目标、规则和专业语言的问题分区；限界上下文是某个模型及其统一语言保持一致的显式边界。

## 子域与限界上下文

- 只有投入、差异化或所有权判断需要时，才把子域标记为核心、支撑或通用；分类必须说明业务依据。
- 使用语言变化、规则所有权、模型一致性和协作契约识别限界上下文，不得直接照搬团队、代码仓库、微服务或数据库边界。
- 同一术语可以在不同上下文拥有不同含义；分别定义后，通过显式翻译连接，不得强制全局统一。
- 每个上下文记录业务目的、模型所有者、统一语言、输入输出和不属于该上下文的概念。

## 上下文映射

每条关系都记录上游、下游、模型所有者、翻译位置、兼容责任和采用理由，并从以下关系中选择最小充分的一种：

- `partnership`：双方共同演进，并共同承担同步成本。
- `shared kernel`：共享一个有意缩小的模型子集，变更需要共同协调。
- `customer-supplier`：上游提供模型或能力，下游作为客户影响上游计划。
- `conformist`：下游主动采用上游模型，不维护翻译层。
- `anti-corruption layer`：下游通过翻译保护自己的模型。
- `open host service`：上游提供稳定、公开的集成协议。
- `published language`：双方通过已发布且稳定的交换语言协作。
- `separate ways`：集成收益不足以覆盖耦合成本，双方保持独立。

关系名称不是结论。无法说明方向、所有权、翻译和兼容责任时，保持为待决事项。

## 完成检查

- 每个关键术语都能指出所属上下文。
- 每个跨上下文交互都能指出关系方向和翻译责任。
- 上下文边界能够由业务语义解释，而不是只由部署或存储拓扑解释。
- 不存在未经说明的全企业规范模型、共享数据库模型或万能公共对象。
