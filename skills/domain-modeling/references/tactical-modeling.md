# 战术领域建模

战术模式只在一个明确的限界上下文内使用。先用业务场景识别身份、状态、行为、不变量和协作，再选择模式；不要求模型包含全部模式。

## 模式采用条件

- **实体**：业务必须跨时间追踪同一身份，属性变化后仍代表同一概念。行为和状态转换应维护自己的不变量。
- **值对象**：由值而非身份定义，等值即可替换；优先保持不可变，并把相关计算放在值对象内。
- **聚合与聚合根**：聚合是事务一致性边界，根负责原子维护边界内不变量。聚合保持小而内聚；外部只通过根和稳定标识引用，不能直接修改内部成员。不得由 UML 组合关系、数据库外键或 API 请求形状推导聚合。
- **领域事件**：表达业务已经发生且业务人员关心的事实，名称使用统一语言。数据库行变化不是领域事件；跨上下文发布时显式区分领域事件和集成事件。
- **领域服务**：承载无法自然归属单个实体或值对象的无状态业务规则。不得把实体行为搬入万能服务。
- **应用服务**：编排用例、事务、授权和外部协作，不持有领域规则。
- **仓储**：为聚合根提供类似集合的读取和持久化边界，不按数据库表或每个实体机械创建。
- **工厂**：只在创建过程复杂、跨多个对象或必须原子满足不变量时使用；简单构造无需工厂。
- **规格**：表达可组合、可命名且有业务意义的判断规则；不得用规格隐藏流程编排或任意查询语法。
- **模块**：按统一语言和概念内聚组织模型，不按技术层或文件数量制造模块。

## 行为与一致性

- 对每个生命周期列出命令、前置条件、守卫、合法和非法转换、产生的事件及转换后不变量。
- 每项不变量必须指出业务所有者、维护它的实体或聚合根，以及强一致边界。
- 跨聚合不变量不得伪装成单事务聚合；记录领域事件、流程协调、补偿或人工处置以及允许的暂时不一致。
- 跨上下文只交换稳定标识、发布语言或集成事件；不得共享可变领域对象。

## 反模式

- 按数据库表一比一创建实体或聚合。
- 把整条业务流程放进巨型聚合。
- 为每个实体创建仓储，或让仓储暴露内部聚合成员。
- 用领域服务堆积本应由实体和值对象维护的规则。
- 把审计日志、消息记录或数据库事件直接称为领域事件。
- 为凑齐 DDD 模式清单创建没有场景、调用方或业务语言依据的空抽象。

模型完成时，每个已采用模式都必须能回指至少一个业务场景、规则或变化压力；不适用的模式只记录理由，不创建占位对象。
