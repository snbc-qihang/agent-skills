# 领域设计治理

完整领域设计以业务场景和可复查的设计源开始，不以接口、服务或部署单元命名开始。`DesignSourceRegistry` 是目标项目内的入口，登记需求、源码、既有 HLD/LLD、API、数据与部署证据的位置，并标记事实、确认、决策和未知项。

按以下顺序产出并保持引用关系：

1. 业务发现：参与者、业务价值、成功/失败/非法场景、验收与术语冲突。场景或能力旅程不是单次请求、API 或实现方法的同义词。
2. 战略设计：领域愿景、核心/支撑/通用子域、业务所有者、变化压力、投入或 make/buy 倾向和边界理由。
3. 系统 HLD：`领域 → 子域 → 限界上下文 → 部署单元` 映射、数据权属、代码根、发布边界、负责人和 Context Map。
4. 边界验证：以模型语境、业务目标、规则权属、变化驱动、稳定复用、质量属性、数据权属和翻译责任审查映射；失败时回到战略设计，不进入详细设计。
5. 每个限界上下文的规范模型：统一语言、不变量、聚合、生命周期、领域事件和集成边界。
6. 每个业务能力或旅程的详细设计：归属一个限界上下文，定义命令、查询、权限、失败处理、外部契约与实现/测试追溯。
7. 变更包：只记录 delta、影响、ADR 与发布回写，不复制或污染基线。

限界上下文是特定模型适用的语义边界，不等同于微服务、部署单元、数据库、仓库、团队或一份详细设计。部署映射可以是一对多、多对一或暂未成立，必须写明原因。一个限界上下文保有一份规范模型，且可以拥有多份能力详细设计。

子域按业务价值、内聚性和战略重要性划分。核心子域说明竞争差异与重点投入；支撑子域说明必要性与适当复杂度；通用子域给出 make/buy/开源倾向，并评估合规、数据、集成和运营成本。高内聚低耦合、单一抽象层次、奥卡姆、最小惊讶和清晰边界是审查问题，不是替代业务证据的标签。

边界校验失败时，在同一运行中保留失败 evidence 与 finding，撤销从战略设计开始的完成状态并回到 `strategic-design`；设计源冻结与业务发现保持有效。技术、团队和部署只可作为可行性约束，不能单独决定子域或限界上下文。

正式产物在业务负责人和架构负责人各自批准前一律为 `reviewing`；自动校验、测试和评审证据不替代双审批，也不能自行提升基线。
