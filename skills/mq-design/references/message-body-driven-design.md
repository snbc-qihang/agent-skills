# MQ 消息体驱动设计的字段边界与旧消息控制

适用场景：需求设计中用户提供了明确 MQ JSON 示例，消费者需要据此保存本地副本或读模型。

## 设计原则

1. 以消息体为字段契约，不要扩展臆测字段。
   - 根字段、业务体、明细数组要逐层展开。
   - 必填/非必填必须按用户示例和注释同步到 MQ 设计、详细设计、数据库设计和测试策略。
   - 消息体没有的字段只能作为“待确认字段来源”，不能直接落 DDL。

2. 对嵌套业务体要写全路径。
   - 示例：`configType=<业务消息类型>` 时，从 `<业务消息类型>` 同名业务体读取 `orderId/tenantId/businessId/eventTime`。
   - 幂等键若引用业务体字段，应写成 `issueId + configType + <业务消息类型>.orderId`，避免误解为根字段。

3. MQ 自动 ACK 原则下，不要显式设计 ack/noack。
   - 业务失败应抛异常，交给容器既有重试/死信策略。
   - 不要在设计文档中增加手工 ack/noack 控制，除非用户明确要求改变系统原则。

4. 多节点乱序不一定要 Redis。
   - 如果用户明确取消 Redis 乱序控制，改用消息事件时间控制：`eventTime > DB source_event_time` 才更新；`<=` 幂等成功结束。
   - 文档中必须说明相同时间戳的处理口径，通常按旧消息/重复消息忽略。

## 输出同步清单

- `message-schema.json`：根字段、业务体字段、明细字段、幂等键、旧消息规则。
- `mq-topic-contract.yaml`：producer/consumer 契约、required/optional 字段、消费者责任。
- MQ Excel：生产者消息体说明、消费者责任、幂等/旧消息控制备注。
- 详细设计：流程图、校验规则、异常表、事务边界、人工评审项。
- 数据库设计：字段映射、唯一键、`source_event_time`、归档/分区约束。
- 测试策略：嵌套消息体解析、必填/非必填校验、旧消息/同时间戳消息、不显式 ack/noack。

## 常见坑

- 用户给的是 `alreadRefundFlag` 这类上游拼写时，数据库可规范成 `already_refund_flag`，但说明里要标注“对应上游 alreadRefundFlag”。
- 如果页面需要手机号/城市/下单时间但 MQ 没给，不要补进 DDL；写成上游补字段或字段来源待评审。
- 不要把“待支付订单副本”误设计成只保存待支付数据；若用户要求保存订单副本，应保存订单状态快照，列表查询再按状态筛选。
