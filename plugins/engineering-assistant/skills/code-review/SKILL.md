# 代码评审

先固定比较点，再分别依据仓库规范和原始需求检查变化的行为。按变更风险选择足够的证据。

1. 固定 base、head、merge-base、diff、需求及用户限制；可调查事实先自行核对，不为已给出的比较点重复请求确认。
2. 从 diff 和相关入口追踪成功、失败、边界、数据及外部影响。可用索引已经返回的内容不重复扫描；工具不可用时沿已知路径定向补齐。
3. 评估正确性、复杂度、冗余、性能、架构和测试质量，报告明确的触发条件、影响、文件位置与验证方法。测试未变不等于覆盖缺失，只有风险需要时补充检查；相关验证通过后不无依据扩大全量测试。
4. 可执行的 active persisted quality node 才提交 `QualitySnapshot` 并遵守六维门禁；内联评审记录判断及不适用理由，不为了获得六个 pass 创建 flow、基准测试或形式化产物。
5. 只有决定性证据闭合触发条件、失败行为和阶段影响时才认定 blocker。证据不足标未核实或未评估，继续独立可完成部分；普通代码走查不以需求 ID 或外部设计源为前提。

需要代码异味判断且仓库规则不足时读取 [异味基线](references/smell-baseline.md)。行为触及身份或授权状态、秘密或持久化合同，读取 [安全 seam](references/security-seams.md) 并闭合数据全部扇出路径。

阶段状态审计、历史产物、工具能力缺口或证据冲突时读取 [证据与阶段审计](references/evidence-and-stage-audit.md)。技术状态与人工批准分别记录，不能用技术通过替代既有人工门禁。

平台已选本 skill 时直接执行内联评审；仅在确实需要持久化门禁或任务超出本原语时进入 Runtime 路由。用户中途修正目标时更新受影响结论并继续未取消的工作。
